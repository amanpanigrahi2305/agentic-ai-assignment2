## Part A · The plan artifact

**`args`.** I chose `args_json`, a single string field per step, because it spends
nothing of Anthropic's 16-union budget, while a `oneOf` with one shape per tool
would spend a union on every step's `args`, and strict mode would only check that
the arguments fit *some* tool's shape. The cost is that strict mode can't see
inside a string, so `ways/planned.py` parses every step's `args_json` before the
plan is allowed to run, checks it against the named tool's own `input_schema`
(argument names, required arguments, and the type of every fixed value), and
checks the filled-in arguments a second time right before each call.

**Strict-mode count.** Every field is required, no field is nullable, and every
object is closed, which gives the schema 0 optional fields and 0 union types
against Anthropic's limits of 24 and 16, and 8 object properties at most 5 levels
deep against OpenAI's limits of 5,000 and 10 (the vendors' published rules as the
assignment quotes them, read on 30 September 2026). Mistral accepted a request with
the plan tool marked `"strict": true`, both in my probe on 15 October 2026 and in
the `plan` call of every planned run, so `strict_compiles` is `true`; but the same
probe showed that Mistral also accepts a strict tool that breaks OpenAI's rules (an
optional field, no `additionalProperties: false`), and since accepting a schema is
not the same as enforcing it, every plan is checked again with
`harness.schema.errors`.

## Part C · Revision at a checkpoint

**The check** (`ways/planned.py`, `checkpoint_check`) runs after the first search,
and after any search that a revision added or changed until `MAX_REVISIONS` is
spent, and passes only if the search returned at least one source file, meaning a
`.ts` or `.tsx` file under `src/`; a search that returns nothing (`no_matches`) or
only documentation, configuration or translation files (`no_source_files`) fails,
and its step is marked failed so the reviser can change it.

**`MAX_REVISIONS = 2`** revision attempts per run, counting accepted and rejected
ones alike. The first is for the normal case: one revision, then a re-check after
the search is retried. The second is a spare, for when the validator rejects a
revision or the retried search fails again.

## Part D · A second pass before posting

The four external checks (`agent/critique.py`, `verify`), in order:

1. **parses**: the draft has a `label:` line set to one of bug, feature, question
   or docs, and a `file:` line set to a path or `none`.
2. **exists**: the path the draft names is a real file under `fixtures/repo`.
3. **seen**: that path appears in the `paths` of at least one of this run's
   `tool_call` lines so far.
4. **agree**: the label and file match: a question names `none`, and a bug,
   feature or docs label names a file.

**`MAX_ROUNDS = 2`** in both `self` and `external` modes: the draft is checked,
rewritten once with the reason it failed, and checked again, and if it still fails
the second check it is held instead of posted, and the run escalates.

Slide 41's three gates, by mode:

| Mode | Can a check find the error? | Does the critic know more than the agent? | A limit and a log? |
|---|---|---|---|
| `off` | No check | No critic | Nothing to limit |
| `self` | Only as an opinion: the same model rereads the same evidence | No: it sees the draft, the issue and the step results, all of which the author already had | Yes: `MAX_ROUNDS`, and one `critique` line per round |
| `external` | Yes, for errors of form: unparsable, a file that doesn't exist, a file the run never saw, or a label and file that disagree. No, for a wrong file the run did see, or a wrong label | Yes: the repository's file list and the run's own trace | Yes: `MAX_ROUNDS`, and one `critique` line per round |

So only `external` passes all three gates, and only for errors that code can
check. A semantic error, such as a wrong label or the right kind of file but the
wrong one, gets through every mode.

## Part E · Detectors and the diff

**How the diff matches a call to a step** (`agent/diff.py`). If a `tool_call` line
names its `plan_step`, it belongs to that step, as long as that step calls the same
tool. If a line doesn't name one (as in the transcribed runs), it goes to the first
step in plan order that is still unmatched, calls the same tool, and has fixed
arguments that all equal the call's. A `"$fill"` argument matches any value. Each
step takes at most one call, and any call no step takes is extra. Among the
matched steps, the longest chain whose calls happen in plan order is marked
executed, and every other matched step is marked reordered. In slide 51's run,

   - **Just-in-time retrieval:** RepoMind already does this, and it is part of why
     its runs stay short. A search returns pointers (at most 20 `path:line:`
     lines), and `read_file` fetches a file only when a step needs it. The longest
     run's largest prompt stayed under 5,000 tokens partly because no file is
     loaded until it is read. The cost is one extra fetch: a `read_file` call per
     planned run.
   - **Compaction:** not needed. With no prompt over 4,730 tokens, there is nothing
     to compact. Forced on at a test threshold, it cost a summarizing call per
     compaction (about 2,700 tokens per run). And without the progress file, the
     six runs could no longer say they had seen any of their 18 earliest paths.
